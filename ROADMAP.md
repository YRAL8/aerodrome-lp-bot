# Aerodrome LP-бот (Base) — дорожная карта

Записано 2026-07-27. Сестринский проект `orca-lp-bot` (Solana/Orca) — тот же
принцип и дисциплина (сначала read-only demo на реальном рынке, потом
независимые аудиты, потом реальные деньги маленькой суммой), но другой стек:
Base — это Ethereum-сеть (EVM), Aerodrome Slipstream — форк Uniswap V3, не
имеет отношения к коду orca-lp-bot.

## Почему этот пул

Через `defi-scanner` (`~/projects/defi-scanner`) с фильтром `--preset mine`
(сравнение с текущим Orca SOL-USDC по реальным комиссиям, без токен-эмиссий)
лидер на 2026-07-27 — Aerodrome Slipstream USDC-cbBTC, ~62.4% реальных
комиссий против ~49% у Orca, TVL ~$9.2M, протокол с 3 аудитами по данным
DeFiLlama, пул отслеживается 373+ дня.

## Фаза 0/1 — read-only демо (сделано 2026-07-27)

- [x] `config.py`, `.env`/`env_template`, `requirements.txt` (`web3`,
      `python-dotenv`, `requests`) — venv создан, зависимости установлены
- [x] `aerodrome.py`: подключение к реальному пулу через `web3.py`, чтение
      `slot0`/`tickSpacing`/decimals обоих токенов, вычисление реальной цены
      cbBTC в USDC из `sqrtPriceX96`
- [x] Демо-позиция (`DRY_RUN=true`, `DEMO_POSITION=true`) — тот же паттерн,
      что в orca-lp-bot: диапазон кэшируется один раз (`_demo_range`), не
      гоняется за живой ценой на каждом вызове (иначе никогда не сможет выйти
      из диапазона — тот самый баг, что был найден и исправлен в самом начале
      проекта Orca, здесь учтён сразу)
- [x] **Баг №1, найден на первом же живом прогоне**: тик нижней/верхней
      границы численно перевёрнут относительно цены (у Uniswap V3 tick растёт
      с сырой ценой token1/token0, а наша "цена BTC в USDC" — это инверсия
      той сырой цены, поэтому tick_lower > tick_upper численно). Функции
      `_price_to_tick`/`_tick_to_price` уже сами корректно учитывают эту
      инверсию — но в `get_position()` была добавлена ВТОРАЯ, лишняя
      перестановка при переводе тиков обратно в цену, из-за чего диапазон
      получался перевёрнутым (нижняя граница больше верхней), и позиция
      показывала "ВНЕ диапазона" даже когда цена была ровно посередине.
      Исправлено: тики читаются напрямую без доп. перестановки. Проверено на
      реальных данных: диапазон $60,165–$70,604, цена $64,770 — корректно "в
      диапазоне", состав 50/50 ($500 USDC + $500 cbBTC).
- [x] `main.py` — разовая проверка статуса (не полноценный monitor-цикл ещё)

## Фаза 1 — мониторинг + Telegram (сделано 2026-07-27, в тот же день)

- [x] Полноценный `monitor_position()` в цикле (`while True` + `asyncio.sleep`),
      с anti-spam на событиях входа/выхода из диапазона (`out_of_range_since`,
      логируется только переход, не каждый тик) — реализовано через
      воркфлоу "архитектор ставит задачу → исполнитель пишет код →
      архитектор проверяет диф и тестирует вживую перед коммитом", коммит `6bda491`
- [x] **Два независимых аудита логики** (независимый аудитор 1, затем
      независимый аудитор 2) — 11 находок суммарно, все
      исправлены и проверены вживую/синтетическими тестами, не просто приняты
      на слово:
      - перепутаны стороны USDC/cbBTC в `_demo_amounts_from_deposit()` при
        выходе цены из диапазона (подтверждено независимым рассуждением, не
        только аудитом) — `4fd8995`
      - `_price_to_tick()`: `int()`-округление (к нулю) вместо `math.floor()`
        для отрицательных тиков; `_align_tick()` теперь флорит нижнюю границу
        и потолкует (`ceil`) верхнюю вместо обеих вниз; checksum-адреса
        токенов; проверка `POOL_ADDRESS`-плейсхолдера до RPC-вызова — `4fd8995`
      - **6 RPC-вызовов на тик → 1** (token0/token1/decimals/tickSpacing
        кэшировались заново каждый раз — это и было настоящей причиной 429 от
        публичного RPC весь день); однострочный баг в собственном же фиксе
        (`<=` вместо `<`); валидация `RANGE_WIDTH_PCT`/`POLL_INTERVAL_SEC` в
        config.py; `DRY_RUN`/`DEMO_POSITION` принимают "1"/"yes"/"on", не
        только "true" — `cb7c748`
      - **демо-P&L был математически заморожен** на сумме депозита (состав
        токенов пересчитывался из живой цены каждый тик, а не фиксировался
        при создании диапазона) — исправлено: количество токенов фиксируется
        один раз при создании диапазона, дальше просто переоценивается по
        живой цене, реально движется вместе с ценой
      - диапазон + `out_of_range_since` теперь переживают перезапуск процесса
        (персистентность в `demo_state.json`, gitignored) — `327d17d`
- [x] Telegram-бот **отдельный** от orca-lp-bot (новый через BotFather,
      `@askeza50_bot`, переименован в отображении на "Aerodrome LP Bot"),
